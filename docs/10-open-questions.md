## 1. 친구 기획 (내일의 주 안건)

### 1-1. 지금 이렇게 구현돼 있습니다

미팅에서 **먼저 이 표를 보여주고 시작**하는 게 빠르다. 기획자가 "이미 이렇게 돼 있구나"를 알아야
수정 요구가 현실적으로 나온다.

| 항목 | 현재 동작 |
|---|---|
| 친구 요청 진입점 | **채팅창 메뉴에서만.** 대화를 나눈 상대에게만 보낼 수 있다 |
| 요청 비용 | **무료.** (대화 신청은 하루 2회 무료 후 루나 5, 친구 요청은 과금 없음) |
| 수락 시 | 이미 살아있는 대화방이 있으면 **FRIEND로 승격**, 없으면 새로 만든다 |
| 슬롯 검사 시점 | 요청할 때와 **수락할 때 양쪽 모두.** 그 사이에 자리가 찰 수 있어서 |
| 최대 친구 수 | **20명**(프라임 30) — ⚠️ 잠정값, 아래 1-2 ① 참고 |
| 거절 | 행을 **삭제**한다 → 나중에 다시 요청할 수 있다 |
| 삭제 | 즉시 관계 해제 + 상시 대화방 종료 + 상대에게 소켓 통지 |
| 친구 대화방 | **24시간 열려 있다.** 매칭 대화만 운영시간(17~06시)을 탄다 |
| 메시지 보관 | 친구 방 **1년**(매칭 방 30일). 친구를 끊어도 방은 FRIEND 기준 |
| 친구 목록 | 접속 상태(온/오프라인) 표시 + 성별·나이대·국가 필터 |
| 오늘의 포스트 | 친구 카드를 누르면 팝업. `friendshipId` 기준이라 **당사자만** 볼 수 있다 |
| 신고·차단 시 | 친구 관계 자동 해제 + 대화방 종료 |

### 1-2. 물어봐야 하는 것

**① 최대 친구 수 — 20명인가 30명인가** 🟢 설정

가장 먼저 정해야 한다. **기획서 안에서 20과 30이 함께 적혀 있어** 지금은
"일반 20 / 프라임 30"으로 해석해 두었다. 이게 맞는지, 아니면 둘 중 하나가 오타인지.

> 답이 무엇이든 `app.friend.max-count` 값만 바꾸면 된다. 오류 문구의 숫자도
> 서버가 값을 실어 보내고 앱이 조립하므로 **자동으로 따라간다.**

**② 친구 요청 진입점을 늘릴 것인가** 🟡 코드

지금은 **채팅창 메뉴 한 곳뿐**이라, 대화를 나눈 적 없는 사람에게는 친구 요청을 보낼 수 없다.
달빛가든에서 마음에 든 사람에게 바로 보내게 할지, 지금처럼 대화가 먼저인지.

> 이건 서비스 성격을 정하는 질문이다. **대화 → 친구** 순서를 강제하면 관계가 무거워지고,
> 바로 요청을 열면 가벼워지는 대신 스팸성 요청이 늘 수 있다.

**③ 친구 요청도 과금할 것인가** 🟡 코드

대화 신청은 하루 2회 무료 후 루나 5인데, **친구 요청은 완전 무료**다. 의도한 것인지.
②에서 진입점을 늘린다면 특히 같이 봐야 한다.

**④ 수락하면 기존 대화방을 이어쓰는 게 맞는가** 🔴 DB 가능성

지금은 나누던 매칭 방을 **그대로 친구 방으로 승격**한다 — 대화 기록이 이어진다.
새 방을 만들어 깨끗하게 시작하는 게 기획 의도라면 관계 모델을 손봐야 한다.

**⑤ 친구 방 24시간 개방을 유지하는가** 🟡 코드

"밤에만 열리는" 것이 서비스 컨셉인데 친구 대화만 예외다. 의도한 차별점이면 그대로 두면 되고,
친구도 운영시간을 타야 한다면 서버 판정과 화면 배너를 모두 바꿔야 한다.

**⑥ 친구를 끊었을 때** 🟡 코드

지금은 **즉시 해제 + 대화방 종료**이고, 곧바로 다시 요청할 수 있다.
재요청 제한(쿨다운)이나 유예 기간이 필요한지. 차단과의 차이를 어떻게 둘지.

**⑦ 친구가 꽉 찼을 때 무엇을 보여줄 것인가** 🟡 코드

지금은 **오류 문구만** 뜬다("친구는 최대 N명까지예요"). 프라임 안내로 이어주는 게 자연스러운데,
그러면 BM 화면과 연결된다.

**⑧ 메시지 보관 1년이 맞는가** 🟢 설정

친구 방 1년 / 매칭 방 30일로 잡혀 있다. 저장 비용과 직결되므로 확인만.

**⑨ 목록 정렬 기준** 🟡 코드

지금은 필터만 있고 정렬 규칙이 명시돼 있지 않다. 접속 중인 사람이 위로 오는 게 자연스러운데
기획 의도가 따로 있는지.

> ⚠️ **미팅 전까지 친구 쪽 코드는 건드리지 않는다.** 수정본과 충돌하면 두 번 일하게 된다.

## 2. 리소스(이미지) 전달

### 2-1. 받을 때 반드시 확인할 3가지

**① 글자가 박히지 않은 배경인가** ← 제일 중요

지금 로그인 배경에는 **"밤에만 만나는 대화 / 오늘, 당신의 밤을 특별한 사람과 함께해요"가
그림으로 구워져 있다.** 일본어로 앱을 켜도 이 두 줄만 한국어로 남는다. **코드로는 못 고친다.**

> 문구는 앱이 얹으므로 **배경에는 글자가 없어야 한다.** 자르는 단계에서 미리 말해두면
> 나중에 다시 요청할 일이 없다. 로고(달빛톡 워드마크)는 브랜드 자산이라 그대로 둬도 되지만,
> **일본어판 워드마크가 필요한지**는 따로 물어볼 것.

**② 원본 출처와 라이선스**

지금 4장은 기획서에 딸려온 것이라 출처가 불명확하다. 스톡이면 상업적 사용 범위가,
AI 생성이면 또 다른 조건이 걸린다. **개발 중에는 문제없지만 스토어 출시 전에는 필수**다.
새로 받는 것도 똑같이 확인해야 한다.

**③ 원본 해상도** — ✅ **확인됨(2026-08-08): 1080×2640 세로**

규격은 [08 체크리스트](08-assets-checklist.md)에 정리돼 있다. **이 문서를 그대로 전달하면 된다.**
앱 아이콘은 **1024×1024 원본 한 장**이면 전 해상도를 코드로 뽑는다.

> ⚠️ **1080×2640은 22:9라 대부분의 폰보다 길다.** 코드가 `alignment: topCenter`라
> **위는 그대로 두고 아래만 잘라낸다** — 20:9에서 아래 240px, 19.5:9에서 300px, 구형 18:9에서 480px.
> 여기에 **상태바·카메라홀(위 ~150px)** 과 **내비게이션 바(아래 ~144px)** 가 별도로 덮인다.
> → 자르는 단계에서 **"위 150px은 상태바에 걸리고, 아래 500px은 잘릴 수 있다"** 고 전해 둘 것.
> 상세는 [08 §1-1](08-assets-checklist.md).

### 2-2. 우선순위 — 이것부터 달라고 할 것

| 순위 | 리소스 | 이유 |
|---|---|---|
| 1 | **앱 아이콘 원본 1024×1024** | 지금 **Flutter 기본 아이콘**이다. 한 장만 있으면 전 해상도 + 스플래시까지 자동 생성 |
| 2 | **로그인·온보딩 배경 4장**(글자 없이) | 라이선스 리스크 해소 + 일본어 문제 해결이 한 번에 |
| 3 | 기본 프로필 이미지 · 빈 상태 일러스트 | 없어도 동작하지만 완성도 차이가 크다 |
| 4 | BM 화면 아이콘(루나·프라임·부스트·패스) | 지금 Material 기본 아이콘으로 대체 중 |
| 5 | 스토어 등록용(피처 그래픽·스크린샷) | 출시 직전에 필요 |

### 2-3. 같이 정해야 할 것

- **커스텀 아이콘셋을 쓸 것인가** — 지금은 Material 기본(`Icons.*`). 쓰면 전부 교체 대상이라 범위가 커진다
- **국기를 이모지로 둘 것인가** — 지금 🇰🇷🇯🇵 이모지라 **기기·OS마다 모양이 다르다.** 이미지로 바꿀지
- **커스텀 폰트(한/일)** — 브랜드 폰트를 쓸 거면 일본어 글자도 포함돼야 한다. APK 용량과 직결
- **WebP 전환** — 배경 4장을 WebP로 바꾸면 용량이 꽤 줄어든다

## 3. 만난 김에 같이 정하면 좋은 것

친구·이미지와 별개지만 **사람이나 계정이 필요해 리드타임이 긴 것들**이다.
지금 못 정하면 그만큼 뒤로 밀린다.

**① 일본어 원어민 검수는 누가 하는가** ← 지금 아무도 안 정해져 있다

`app_ja.arb` **449키가 전부 AI 초벌**이다. 한·일 매칭 앱에서 일본어가 어색하면 그대로 이탈이다.
특히 **BM 화면(구매 유도 문장)** 과 **오류 문구 61종**은 한 번도 검수를 안 거쳤다.

> 검수본은 **엑셀이나 텍스트로 받으면 된다**(키 = 지금 문구 = 수정안). 받으면 ARB만 고치면 되고
> 코드는 안 건드린다. **누구에게 맡길지만 정하면 우리 쪽 작업은 반나절이다.**

**② 개발자 계정·키를 누가 언제 발급하는가**

| 필요한 것 | 비용 | 열리는 작업 |
|---|---|---|
| LINE · KAKAO · GOOGLE 소셜 키 | 무료 | **실제 로그인** (지금은 개발용 목 로그인) |
| Google Play 개발자 | $25 1회 | 인앱결제 상품 등록, 영수증 실검증, 스토어 출시 |
| Apple Developer | $99/년 | iOS 출시 (+ **Mac 실물 필요**) |
| DeepL 또는 Google 번역 API | 종량제 | **실시간 번역** — 판정 로직은 이미 다 붙어 있고 키만 없다 |
| AdMob | 무료 | 광고 + '광고 제거' 혜택이 짝을 이룬다 |

> 발급에 시간이 걸리므로 **신청만 미리 걸어두면** 다른 작업과 대기시간이 겹친다.

**③ 6개월 프라임의 부스트를 언제 주는가** 🟢 설정

일괄 지급(가입 즉시 6개월치)과 매월 지급 중 어느 쪽인지. 기획서에 없다.

**④ 출시 목표와 순서** — ✅ **한·일 동시 오픈 확정(2026-08-08)**

동시 오픈이면 **일본어가 "나중에 다듬을 것"이 아니라 출시 조건**이 된다. 아래가 따라온다.

| 따라오는 것 | 왜 |
|---|---|
| **일본어 원어민 검수가 출시 블로커** | 한국 먼저였다면 뒤로 미룰 수 있었다. 이제 못 미룬다 → ①번을 **가장 먼저** 정해야 함 |
| **LINE 로그인 키 우선** | 일본에서는 LINE이 주력이다. 소셜 3사 중 발급 순서를 정해야 하면 LINE부터 |
| **스토어 리스팅 일본어판** | 앱 설명·스크린샷·키워드를 일본어로도 준비해야 한다([08](08-assets-checklist.md) 17번 항목이 2배가 된다) |
| **가격 표기** | 루나·프라임 가격이 원화 기준이다. **엔화 가격을 따로 정할지** 스토어 환율 자동 변환에 맡길지 — 새로 정해야 함 |

**아직 안 정해진 것**
- **iOS를 포함하는 시점** — Mac + Xcode가 있어야 해서 준비 기간이 따로 필요하다
- 인프라(AWS 등) 호스팅 — 서버 개발자가 맡기로 한 부분이라 일정만 맞춰두면 된다
- 위 표의 **엔화 가격 정책**
