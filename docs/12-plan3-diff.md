## 0. 한 줄 요약

**앱의 근본 전제 하나가 사라지고, 도메인 하나가 통째로 생겼다.**

- 🔴 **야간 운영시간(17~06시) 게이트가 없어졌다.** 24시간 열린다.
  대신 **"하루"의 경계가 KST 18시**로 바뀌었다(모든 초기화가 18시 기준).
- 🔴 **달빛 한마디 이벤트(§8)가 신설**됐다 — 매일 질문 하나, 한마디+사진으로 답하고 목록·댓글·좋아요.
  기존에 없던 **완전한 신규 도메인**이다.
- 🔴 **달빛가든에 열람 제한이 생겼다** — 무료 사용자는 상대 **메인 사진 1장만**,
  전부 보려면 **매일 내 새 사진 1장을 올려야** 한다.
- 🟡 예고돼 있던 변경 셋이 **모두 현실화**됐다 —
  게이트 폐지([04 §4-1](04-progress-and-roadmap.md)), 친구 제한 과금 무관 통일(§4-2), 대화 신청 수락 흐름 변경(§4-4).

## 2. 새로 생긴 것

### 2-1. 달빛 한마디 이벤트 (§8) — 신규 도메인 🔴

매일 하나의 질문에 **한마디(최대 100자) + 사진 1장(선택)** 으로 답하고 서로 보는 이벤트.
달빛가든 상단의 `[달빛 한마디]` 버튼으로 들어간다.

| 화면 | 내용 |
|---|---|
| 타이틀 | 오늘의 질문, 참여자 수, **남은 시간 카운트다운**, [참여하기] |
| 목록(8-1) | **최신순 / 인기순** 정렬(인기순 = 좋아요+댓글 합), 카드에 사진·좋아요·댓글 수, `[내 한마디]` |
| 상세(8-2) | 사진 검색, 좋아요, **댓글 3단계**, 댓글 50자, **이미지 첨부 1장**, 번역 |
| 작성(8-3) | 한마디 100자, 메인 이미지 1장(선택) |

- **KST 18시에 모든 정보가 초기화**되고 새 질문이 나온다.
- 내 글이 없을 때 `[내 한마디]`를 누르면 안내 문구.
- 번역은 **댓글창 5회 호출까지 무료**.

### 2-2. [포스트 정보] 화면 — 신규 공통 화면 🔴

여러 곳에서 불리는 **상대 정보 풀스크린**이다. 상대 포스트 사진(1/9 인디케이터) + 관심사 + 소개 한마디 +
우상단 ⋮(프로필 보기·신고·차단). **호출한 곳에 따라 하단 버튼이 달라진다.**

| 어디서 불렀나 | 하단 버튼 |
|---|---|
| 대화방 [받은 신청] | **거절 / 수락** ← 매칭 결정이 여기로 옮겨졌다 |
| 대화 목록, 상대가 "친구" | 대화 하기 |
| 대화 목록, "친구 신청" 상태 | 친구 신청 |
| 대화 목록, "신청 대기" 상태 | 닫기 |
| 친구 목록 | 대화하기 (+ 친구해제) |
| 친구 [받은 신청] | 수락 / 거절 |

### 2-3. 달빛가든 열람 제한 🔴

- 무료 사용자는 상대의 **메인 사진 1장만** 볼 수 있다.
- 전부 보려면 **매일 자신의 신규 사진 1장 등록**이 필요하다. **KST 18시 초기화.**
- 미등록 상태에서 **2번째 사진을 호출하면** 하단에 [사진 등록 안내창].
- 프라임·앨범패스는 무제한.

> 이건 단순 제한이 아니라 **매일 사진을 올리게 만드는 장치**다. 포스트 등록률과 직결된다.

### 2-4. 포스트 메인 사진 지정 🟡

`[메인]` 버튼으로 달빛가든에 노출할 대표 사진을 고른다.
- 최초 사진은 자동 메인. **메인을 지우면 다음 슬롯이 자동 메인.**
- 신규 사진은 등록 시간순 슬롯(1번이 최신).

## 4. 흐름이 바뀐 것

### 4-1. "하루"의 경계: 06시 → **KST 18시** 🔴

기획서 전반이 **18시 초기화**로 통일됐다(사진 삭제 횟수, 가든 열람 조건, 좋아요·댓글 수치,
매력 전환율 점수, 달빛 한마디). 화면에도 *"매일 저녁 6시에 새로운 미션이 열려요"* 로 나온다.

우리 `session_date`는 **게이트 06시 기준**이고 **6개 테이블**이 이걸 쓴다
(`posts`·`daily_usage`·`feed_skips`·`daily_translate_targets`·`boost_activations`·`post_stats`).
→ **경계를 18시로 옮기는 마이그레이션**이 필요하다. [11 §2-1](11-change-impact-map.md) 참고.

### 4-2. 달빛가든 노출 알고리즘 — 구체화되고 바뀜 🔴

기획서가 **공식을 숫자까지 명시**했다. 지금 우리 스코어(`score-pick` 50 / `score-online` 10)와 다르다.

```
Post Score = Online Point + Post Recency Point + Engage Point

Online   : 접속 중 10 / 미접속 0
Recency  : 1시간 이내 30 / 1~3h 20 / 3~5h 10 / 5h 초과 0   (사진 갱신 시에도 적용)
Engage   : 전환율 = {(좋아요×1)+(댓글×2)+(1:1대화요청×4)} / 총 노출 횟수 × 100
           30%↑ 30 / 20%↑ 20 / 15~19.9% 15 / 10~14.9% 10 / 5~9.9% 5 / 그 이하 0
           * 총 노출 20회 미만이면 Engage 0
           * 전환율 점수만 18시 초기화(나머지는 초기화 안 함)
```

같이 바뀌는 규칙:

| 규칙 | 내용 | 지금 |
|---|---|---|
| **노출 순서 고정** | 가든 진입 시 **1회 산정**, 그 세션 동안 순서 유지 | 매 요청 셔플 → **[07 §5-2 부채의 정답이 이것이다](07-work-log.md)** |
| **15분 노출 제외** | 한 번 노출된 상대는 그 사용자에게 15분간 제외 | `feed_skips`는 세션(하루) 단위 |
| **풀 소진 시 반복** | 다 보면 처음부터 다시 | V8 스킵 복귀와 취지는 같음 |
| **부스트 별도 풀** | 부스트 사용자는 **별도 풀**로 순위를 매긴다. 구매 즉시 **3회 노출 우선권**(⚠️ 미결, §6 B3) | 없음 |
| **6:4 믹싱** | 일반:부스트를 **6:4로 랜덤 믹싱**해 순차 노출. 부스트가 더 많으면 비율 반대 | 없음 |
| **노출 횟수 집계** | 스킵·동일인 검색·좋아요도 **1회 노출로 산정** | `post_stats`에 노출 수는 있으나 이 정의와 다를 수 있음 |

### 4-3. 대화 신청 수락/거절 — 목록에서 [포스트 정보] 화면으로 🟡

지금은 대화방 목록에 **카드가 뜨고 그 자리에 수락/거절 버튼**이 있다.
Plan_3은 **받은 신청이 그리드 카드**이고, 카드를 눌러 **[포스트 정보] 화면에서** 수락/거절한다.
상대의 포스트 사진·관심사·소개를 보고 결정하라는 의도다.

### 4-4. 친구 신청 진입점 3곳으로 🟡

| 지금 | Plan_3 |
|---|---|
| 채팅창 메뉴 한 곳 | ① 채팅창 `[친구 신청]` 버튼 ② 채팅창 내 프로필 보기 ③ **대화방 목록의 `[친구 신청]` 버튼** |

- **프로필 보기 버튼 명칭이 문맥을 탄다** — 채팅창 안에서는 "친구 신청", 밖에서는 "대화 신청".
- 신청이 오면 상대 **주메뉴 [친구]에 빨간 점** 알림.
- 같은 채팅방에 함께 있으면 **채팅창 위에 팝업으로 즉시** 띄운다.

### 4-5. 친구 목록 정렬 규칙 명시 🟢

**최신 > 온라인 > 최근 접속** 순. 지금은 정렬 규칙이 없다([10 §1-2 ⑨](10-open-questions.md)의 답이 이것).

### 4-6. 대화 목록 미리보기 — 이미지·음성 **제외** ⚠️

> *"대화 목록의 메시지는 대화 마지막 문장을 최대 25자까지만 출력 **(이미지 및 음성 제외)**"*

✅ **답: 종류를 그대로 표기한다** — 이미지면 "이미지", 음성이면 "음성 메시지".
"제외"는 **본문 25자 미리보기의 대상이 아니라는 뜻**이지 빈칸으로 두라는 게 아니었다.

→ 2026-08-23에 음성을 "음성 메시지"로 고친 것이 **맞는 방향이었다.**
채팅에 이미지(GIF 포함)가 들어오면 **"이미지" 표기도 같은 방식으로** 추가한다.

- ⏳ **"구매 즉시 3회 노출 우선권"만 아직 불명확하다.** 구매 직후의 별도 특례로 보이는데,

## 6-1. D2를 다시 정리 — "전환 시점에 걸친 데이터"가 무슨 말인가

**질문의 뜻**: `session_date`(영업일)의 **경계 시각이 06시에서 18시로 옮겨질 때**,
이미 저장돼 있는 행들을 어떻게 볼 것이냐는 이야기다.

**지금 구조**
- `session_date`는 "이 활동이 며칠 회차인가"를 나타내는 날짜 한 칸이다.
- 지금은 **06시가 경계**다 → `8/29 07:00 ~ 8/30 05:59`의 활동이 모두 `session_date = 2026-08-29`.
- 이걸 쓰는 테이블이 **6개**다: `posts`(오늘의 포스트가 무엇인가) · `daily_usage`(무료 횟수) ·
  `feed_skips` · `daily_translate_targets` · `boost_activations` · `post_stats`.

**18시로 옮기면 무슨 일이 생기나**
- 새 기준으로는 `8/29 18:00 ~ 8/30 17:59`가 `2026-08-29` 회차가 된다.
- **바꾸는 순간, 이미 저장된 행의 날짜는 옛 기준으로 찍혀 있다.** 두 기준이 한 테이블에 섞인다.
- 예를 들어 **8/29 정오에 배포**하면, 그날 아침에 쓴 무료 횟수는 옛 기준으로 `8/29`인데
  새 기준으로는 아직 `8/28` 회차다 → 사용자 입장에서 **횟수가 초기화된 것처럼 보이거나, 반대로 안 된 것처럼 보인다.**
- `posts`가 특히 문제다. "오늘의 포스트"는 `(user_id, session_date)`로 하나인데,
  경계가 바뀌면 **한 회차가 두 날짜로 쪼개지거나 두 회차가 한 날짜로 합쳐진다.**

**할 수 있는 것**

| 방법 | 내용 | 평가 |
|---|---|---|
| (a) **18시 정각에 맞춰 배포** | 옛 회차가 막 끝나고 새 회차가 시작되는 지점이라 **겹침이 없다** | ✅ 출시 후에는 이게 정답 |
| (b) 개발 DB를 비운다 | 지금 데이터는 테스트용뿐이다 | ✅ **지금은 이걸로 충분** |
| (c) 마이그레이션에서 재계산 | 기존 행의 `session_date`를 새 기준으로 다시 찍는다 | 데이터가 많아지면 필요. 지금은 과하다 |

> **결론**: 지금은 **(b)** — 개발 DB를 비우고 새 기준으로 시작한다.
> 다만 **(a)를 규칙으로 문서에 남긴다** — 출시 후에 영업일 경계를 또 건드릴 일이 생기면
> **반드시 경계 시각에 배포**해야 한다. 이건 데이터가 쌓인 뒤에는 되돌리기 어려운 종류의 실수다.
