**서버 (Spring Boot)** — 서버 개발자 초기 구현 + 로컬 빌드 환경 구축
- 인증(소셜 로그인 추상화)·프로필 도메인 실동작, 공통 인프라(JWT 인터셉터·스토리지 추상화·예외/CORS), Flyway V1 스키마, MyBatis.
- **로컬 풀스택 구동 완료(2026-08)**: JDK 17 + Gradle 8.10.2 + **로컬 MariaDB 11.4.5** → Flyway V1 스키마 적용, **Spring Boot 8080 구동 성공**(`/system/gate` 200, 인증 401). 세팅 절차 = [06 개발환경](06-dev-environment-setup.md).
  - MariaDB 11.4 호환 이슈 1건 수정: `chat_rooms.active_pair_key` 생성컬럼→앱세팅(커밋 `40d9130`). REST 날짜=ISO-8601 확인.
- 구현 완료(서버): auth/profile · post · garden · chat(+WebSocket) · friend · luna · **store(BM)** · scheduler. Flyway **V6**까지 적용.

**앱 UI — 화면 11개** (정적, 다크 테마 고정, Android 에뮬레이터 검증 완료)
- 로그인 → 온보딩 3단계(닉네임 · 출생년도 · 성별/국가)
- 메인 셸(하단 5탭 IndexedStack):
  - 포스트(오늘의 포스트/홈) · 달빛가든(피드) · 대화방 → 채팅창 · 친구 · 프로필
- 디자인 시스템(`app_colors`/`app_dimens`/`app_theme`), feature-first 구조, 공용 하단 내비(`MainBottomNav`)

> 현재는 "정적 UI" = 코드로 만든 화면 + 더미 데이터/사진. 상호작용(입력·검증·탭 전환·화면 이동)은 동작하나, 서버 데이터·실기능은 미연결.

### 4-1. 운영시간 폐지 가능성 — 하루 종일 열림

"밤에만 열린다"는 이 앱의 핵심 제약이었다. 이게 없어질 수 있다.

| 흔들리는 것 | 비용 | 왜 |
|---|---|---|
| 서버 판정 | 🟢 **설정** | `requireGateOpen()` 호출 10곳(chat 3 · garden 4 · post 3). `app.gate.open-hour=0`이면 항상 열린다 — **개발용 우회로 이미 쓰고 있는 값**이다 |
| 화면 분기 | 🟡 코드 | `GateClosedView`·`GateBanner`·카운트다운. 지우는 쪽이라 어렵진 않다 |
| **영업일(`session_date`)** | 🔴 **DB** | **여기가 진짜다.** 6개 테이블이 이 기준으로 묶여 있다 — `posts` · `daily_usage` · `feed_skips` · `daily_translate_targets` · `boost_activations` · `post_stats`. 24시간이 되면 **"하루"의 경계를 새로 정해야 한다**(자정? 06시 유지?) |
| 스케줄러 | 🟡 코드 | 06시 매칭방 일괄 종료 + `SYSTEM_CLOSE`의 의미가 사라지거나 바뀐다. 06:05 일일 정리도 경계를 따라간다 |
| 포스트 등록 창 | 🟡 코드 | `window_started_at` · `remainingUploadSeconds` — "등록 가능 시간"이 상시라면 개념이 없어진다 |
| 문구·이미지 | 🟡 | ARB **게이트 전용 14키**(`gardenGateTitle`·`chatGateClosed`·`gateOpensIn`·카운트다운 3종·`error*GateClosed` 4종 등) + 로그인의 "오후 5시 ~ 새벽 6시" + **이미지에 구워진 문구까지** |

> ⚠️ **판정을 끄는 건 설정 한 줄인데, 도메인 개념(영업일)과 리소스가 비싸다.**
> "게이트만 열면 되는 거 아닌가"로 접근하면 `session_date`에서 막힌다.

### 4-2. 친구 제한을 과금과 무관하게 통일

지금은 **일반 20 / 프라임 30**이고, 분기는 `FriendService.requireFriendSlot()` **한 곳**뿐이다.

- 숫자를 합치는 것 자체는 🟢 **설정 + 분기 제거**로 끝난다. 오류 문구의 숫자도 서버가 `field`로 실어 보내고
  앱이 ARB placeholder로 조립하므로 **자동으로 따라온다.**
- **진짜 영향은 BM이다.** 프라임 혜택 목록에서 "친구 30명"이 빠지면 **프라임의 가치 구성이 바뀐다** —
  상점 화면(25~30)의 혜택 표시와 문구를 다시 봐야 한다.
- 기획 측 표현이 "관련 기획안들도 크게 바뀔 수 있다"이므로,
  [10 §1](10-open-questions.md)의 **친구 9항목이 통째로 다시 열린다**고 보는 게 맞다.

> ⚠️ **친구 영역 동결은 계속 유지한다.** 지금 손대면 두 번 일한다.

### 4-3. 폰트 UI를 이미지로 전환 — 이쪽으로 간다

**서비스 국가가 한·일 둘뿐이라 언어별 이미지 세트가 감당된다**는 판단이다.
오늘 적용한 달빛가든이 이미 그 방식이다 — 버튼·필터 칩의 글자가 전부 이미지다.

이미 굳혀 둔 원칙([07 싱크 요약 ④](07-work-log.md#4-세션-로그))의 확장이다:
**UI의 언어는 두 종류 — 폰트(ARB)와 이미지.** 이미지 속 글자는 결함이 아니라 설계이고,
일본어판은 **일본어가 박힌 이미지를 따로** 받는다.

**반드시 폰트로 남아야 하는 것** ← 여기가 제일 중요하다

| 종류 | 왜 이미지가 안 되나 |
|---|---|
| **placeholder가 들어가는 문구 — 현재 56키** | 이미지는 **값을 끼울 수 없다.** `{nickname}님`, `{days}일 남음`, `친구는 최대 {n}명`. 서버가 숫자를 `field`로 실어 보내는 구조 전체가 여기에 걸려 있다 |
| 사용자 입력 | 닉네임·하루 한 마디·채팅 메시지·댓글 |
| 오류 문구 61종 | 상황이 계속 늘어난다. 서버 `ErrorCode`가 추가될 때마다 이미지를 새로 받을 수는 없다 |
| 긴 안내문 | 줄바꿈이 기기 폭을 타므로 래스터로 고정하면 잘리거나 남는다 |

→ **이미지로 갈 수 있는 것은 "고정된 짧은 라벨·버튼·타이틀"** 로 한정된다.

**치르게 되는 비용**
- 이미지 세트가 **ko/ja 2배** + 해상도별. APK 용량이 늘어난다(WebP 전환 검토가 여기서 의미를 갖는다)
- **문구 오타 하나 고치는 데 디자이너 재발주.** 지금은 ARB 한 줄이면 끝나는 일이다
- 접근성 — 스크린리더가 못 읽고, 사용자의 글자 크기 설정을 무시한다
- 얇은 선·단순 도형은 **여전히 이미지로 받지 말 것**(함정 #31 — 코너가 스케일을 안 받아 찌그러진다)

**검수의 성격이 바뀐다**: 일본어 원어민 검수 결과물이 `app_ja.arb` 수정본만이 아니라
**이미지 발주용 일본어 원고**도 된다. 받는 형식(엑셀·텍스트)은 같아도 **쓰이는 곳이 둘로 갈린다.**

### 4-4. 대화 신청 수락/거절 흐름 변경 가능 (2026-08-23 공유)

**지금은 기획서에 있던 대로다.** 우리가 만들어낸 화면이 아니다 —
[01 §1.6](01-protocol-api-spec.md)의 화면 번호 열이 근거다(`/chat/rooms` → **화면 11**,
`/chat/rooms/sent` → **화면 12**, `:accept`·`:reject` → **화면 11**).

| 지금 흐름 |
|---|
| 달빛가든에서 **대화 신청**(하루 2회 무료, 이후 루나 5) → 상대의 대화방 목록 상단에 신청이 쌓임 |
| 상대가 **수락**해야 대화방이 생긴다. 거절하면 신청이 사라진다 |
| 내가 보낸 신청은 별도 탭(화면 12)에서 상태를 본다 |

| 바뀌는 것 | 비용 |
|---|---|
| 수락/거절 **UI 위치·모양** | 🟡 클라 화면만 |
| 수락 **없이 바로 대화방 생성** | 🟡 서버 로직 + `chat_requests`가 **존재 이유를 잃는다** |
| 신청 개념 자체를 다른 방식으로 | 🔴 관계 모델 재설계 |

> ⚠️ **"수락"이라는 단계가 없어지면 🔴다.** `chat_requests` 테이블과 소켓 op `CHAT_REQ_INCOMING`이
> 통째로 쓸모를 잃고, 대화 신청의 **루나 과금이 걸리는 지점**도 옮겨야 한다(지금은 신청할 때 뺀다).
>
> ⚠️ **친구 기획과 얽혀 있다.** 지금은 *대화 신청(수락 필요)* 과 *친구 요청(수락 필요)* 이
> 별개의 두 흐름이다. [10 §1](10-open-questions.md)의 ②(요청 진입점)·④(수락 시 방 승격)를
> 함께 봐야 한다 — 한쪽만 바꾸면 두 흐름이 어긋난다.

**그때까지**: 대화 신청·수락·거절 쪽 코드는 손대지 않는다(친구 영역과 같은 이유).

### 4-5. 셋이 겹쳐서 나오는 결론 — 지금 하면 안 되는 것

🚨 **일본어 검수를 전량으로 발주하면 낭비가 난다.**

- 4-1이 실현되면 **게이트 문구 14키가 사라진다**
- 4-2가 실현되면 **친구 문구가 바뀐다**
- 4-3이 실현되면 **상당수가 ARB가 아니라 이미지 원고**가 된다

**그렇다고 미루면 안 된다** — 한·일 동시 오픈이라 검수는 여전히 **출시 블로커**다.
**범위를 나눠 흔들리지 않는 것부터** 먼저 돌리는 게 맞다.

| 지금 검수해도 되는 것 | 확정 후로 미룰 것 |
|---|---|
| 온보딩 · 프로필 · 상점/BM · 공통 라벨 | 게이트 관련 14키 (4-1) |
| 오류 문구 61종 중 **게이트 4키를 뺀 나머지** | 친구 관련 문구 (4-2) |
| 관심사 37종 · 지역 20곳(고유명사) | 이미지로 옮겨갈 라벨 (4-3) |
