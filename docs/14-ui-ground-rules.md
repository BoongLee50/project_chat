# UI 작업 대전제 (GROUND RULES)

> 🚨 **UI를 건드리기 전에 이 문서를 먼저 읽는다.** 짧게 유지한다 — 길어지면 아무도 안 읽는다.
>
> - **확정**: 2026-09-14 (기획 지시)
> - **적용 범위**: 지금부터 들어가는 모든 UI. **이 UI는 실제 라이브까지 갈 확률이 높다.**
> - 예외가 있을 수 있지만, **의심스러우면 아래를 따른다.**

---

## 1. 언어는 **한국어와 일본어 둘뿐**이다

추후 늘어날 수 있어도 **이 둘이 최우선**이다. 셋째 언어를 가정해 구조를 미리 복잡하게 만들지 않는다.

- ARB는 `app_ko.arb`(원문) / `app_ja.arb` 두 벌. 폴백은 한국어.
- 영어판은 **없다.** 한·일 서비스에 영어 UI는 양쪽 모두에게 제2외국어다.
  (`TOP`·`PICK`·`Prime`처럼 **이미 영어로 디자인된 라벨**은 그대로 둔다 — 두 언어 모두에서 통하고
  언어별 두 벌이 필요 없다. 새 리소스에도 이 패턴은 써도 좋지만, 있는 한국어 그림을
  영어로 갈아엎지는 않는다.)

## 2. 🚨 그림에 글자가 붙어 있으면, **글자가 아니라 그림이 통째로 바뀐다**

이게 이 앱에서 가장 자주 틀리는 지점이다.

| | |
|---|---|
| **하는 것** | 언어 설정에 따라 **이미지 파일 자체를 교체**한다 |
| **하지 않는 것** | 그림 위에 ARB 문구를 얹거나, 그림 속 글자를 폰트로 다시 그리는 것 |

**이미지 속 한글은 "덜 번역된 상태"가 아니라 의도된 상태다.** 폰트로 대체하려 들지 말 것.

```
assets/images/post/empty_bg.png      ← 한국어(원문, 기본 자리)
assets/images/post/ja/empty_bg.png   ← 일본어(같은 파일명, ja/ 하위 폴더)
```

### 코드에서는 신경 쓸 게 거의 없다 (2026-09-14 정비)

**`ArtImage`로 그리는 그림은 자동으로 언어별 경로를 거친다.** 호출부는 원문 경로만 알면 된다.
직접 `Image.asset`을 쓰는 자리만 `DesignCanvas.localizedAsset(context, 경로)`로 감싼다.

🚨 **규격도 언어를 따른다.** 일본어 글자는 폭이 제각각이라(「月光ガーデン」은 `달빛가든`의 1.6배)
원문 상자에 그리면 눌린다. 그래서 목록에 **일본어판 규격을 함께** 적고 `ArtImage`가 그 크기로 그린다.
⚠️ 그래도 **자리보다 넓을 수 있다** — 받은 주메뉴 글자 두 장이 탭 한 칸을 넘어서
칸 안으로 줄여 그리고 있다(`MainBottomNav._fitInSlot`). 규격이 맞는 그림이 오면 저절로 안 걸린다.

**일본어판이 있는 그림은 `DesignCanvas.localizedAssets`에 적혀 있고, 적힌 것만 경로가 바뀐다.**
목록에 없으면 **한국어 원문이 그대로 나간다** — 일본어판이 오기 전에 미리 감싸 두어도 안전하다.

> 🚨 **그래서 일본어판이 없어도 깨지지 않는다.** 예전에는 일본어 로케일이면 파일 존재 여부와
> 무관하게 `ja/` 경로를 만들어서, **일본어 사용자에게만 그림이 깨지고 한국어로 테스트하는
> 우리는 영영 몰랐다.** 한국어가 잠시 보이는 편이 깨진 자리보다 낫다.

**일본어판 파일이 왔을 때 할 일은 셋뿐이다:**

1. `ja/`에 **같은 파일명**으로 넣는다
2. `DesignCanvas.localizedAssets`에 **원문 경로 한 줄** 추가
3. 새 폴더였다면 `pubspec.yaml`에 `- .../ja/` 줄 추가 → **`flutter clean` 후 재빌드**

호출부는 손대지 않는다. `ArtImage`를 쓰는 **모든 자리가 한꺼번에** 바뀐다.

> 📌 **`test/localized_assets_test.dart`가 이 넷을 대신 지킨다** —
> ① 등록했는데 파일이 없다 ② `pubspec.yaml` 줄을 빠뜨렸다
> ③ **두 판의 규격이 다르다**(레이아웃이 틀어진다) ④ `ja/`에 파일만 넣고 등록을 안 했다.
> 넷 다 **일부러 깨뜨려 실제로 잡히는 것까지 확인**했다.

현재 두 벌이 갖춰진 것은 `post/empty_bg.png` **하나뿐**이고,
아직 못 받은 **20장 목록**은 [08 §0-1](08-assets-checklist.md)에 있다.

**그림이 이미 말하고 있으면 글자를 또 그리지 않는다.** 빈 상태 배경에 안내가 구워져 있는데
그 위에 ARB 문구를 얹었다가 **같은 말이 두 번** 나온 적이 있다([07](07-work-log.md) 2026-09-06(2)).

## 3. 폰트로 그리는 글자는 **상태·수치 표시**가 기본이다

화면에 고정으로 박히는 **라벨·타이틀·버튼 문구는 그림**이 가져간다.
폰트(ARB)가 맡는 것은 **값이 변하는 것**이다 — 개수, `보유중`, `진행중`, `없음` 같은 상태.

📌 **실무 경계**(이 저장소의 해석 — 기획과 어긋나면 기획이 맞다):

| 폰트로 그린다 | 그림이 가져간다 |
|---|---|
| 수치·개수(`3/9`, `★ 80`, 남은 횟수) | 화면 타이틀, 하단 주메뉴 라벨, 필터 칩 라벨 |
| 상태(`보유중`·`진행중`·`없음`·`온라인`) | 버튼에 박힌 고정 문구(`포스트 공유하기`·`부스트`) |
| **서버가 준 것**(오류 문구, 상대 닉네임·소개·메시지) | 브랜드 조어(`달빛가든`·`달빛 한마디`) |
| 사용자가 입력하는 칸(힌트·글자 수) | 배경에 구워진 안내문 |
| 팝업 본문·확인 문구 | |

즉 **ARB가 없어지는 게 아니다.** 오류·팝업·입력 폼·서버 문구는 그림으로 만들 수 없다.
줄어드는 것은 **"화면에 고정으로 박히는 라벨"** 쪽이다.

🚨 그래서 규칙 하나가 그대로 살아 있다 — **숫자를 문구에 굳히지 말 것.**
한도·잔여 횟수는 서버가 값으로 싣고 ARB가 조립한다(`대화 신청 (무료 2회)`).

## 4. 예외는 있을 수 있다 — 다만 **혼자 정하지 않는다**

위 셋과 어긋나는 자리가 나오면, 임의로 폰트/그림을 바꾸지 말고
[10 미결 질문](10-open-questions.md)에 적어 기획에 확인한다. 특히:

- 시안에 없는 문구를 화면에 새로 만들어야 할 때
- 그림 속 문구가 기획서 본문과 다를 때 → **본문을 따른다**(2026-09-06 선례)
- 그림이 낡아 내용이 틀렸을 때 → 코드로 못 고친다. **새 그림을 요청한다**
  (`login_bg.jpg`에 폐지된 *"밤에만 만나는 대화"* 가 박혀 있는 것이 지금도 미해결이다)

---

## 그림을 요청할 때 반드시 붙일 말

1. **한 자리에 놓이는 그림은 "같은 규격으로"** — `ArtImage`가 시안 원본 픽셀을 상수로 들고 있어서,
   규격만 같으면 **코드를 한 줄도 안 고치고** 교체된다(`달빛 한마디` 335×96 → 일본어도 335×96).

2. 🚨 **다만 여러 개가 한 줄에 나란히 서는 자리는 기준이 다르다 — "제 칸 안에"** 이다.
   하단 주메뉴 글자가 그렇다. **"한국어와 같은 폭으로" 요청하면 오히려 나빠진다** —
   `달빛가든`이 146인데 「月光ガーデン」 여섯 글자를 146에 넣으면 글자가 더 작아진다.
   맞는 기준은 **탭 한 칸(≈196px) 안**이고, 지금 받은 232·234는 그걸 넘는다.

   > 📌 **196에 맞춰 다시 받아도 결과는 지금과 거의 같다.** 여섯 글자를 196에 넣으면
   > 글자 높이가 34 근처가 되는데, 코드가 넣고 있는 보정(84% 축소)과 사실상 같은 그림이다.
   > **글자를 크게 하고 싶으면 규격이 아니라 문구를 줄여야 한다**
   > (「月光ガーデン」→「ガーデン」·「プロフィール」→「プロフ」).
   > 일본어 문구는 어차피 원어민 검수를 거치므로 **그때 라벨 길이를 함께 정하는 것**이 한 번에 끝내는 길이다.

3. **일본어는 글자가 길어지기 쉽다** — 캔버스를 키우지 말고 **글자를 자리에 맞춰** 달라고 할 것.
3. **좌표는 1080 캔버스 픽셀값**으로(Plan_4 표기). `*_참고용.png`는 옛 표기라 섞어 읽으면 28배 어긋난다.
